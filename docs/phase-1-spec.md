# Phase 1 Spec: First-Party Tracking and Order Stitching

**Status:** Approved with default decisions (see the end of this document).

## Goal

For every Shopify order, answer: **which visitor placed it, and what marketing touchpoints did that visitor have before buying?**

Phase 1 is done when:

1. Storefront visits are recorded with their marketing source (UTMs, click IDs, referrer).
2. Checkout events from Shopify are linked to the same visitor.
3. Every new order arrives through a verified webhook and is stitched to a visitor where possible.
4. Historical orders are backfilled.
5. A debug page shows, for any order, the matched visitor, the touchpoint timeline and how the match was made.

**Out of scope for Phase 1:** dashboards and reports, multi-touch or data-driven models, ad platform spend imports, conversion APIs (Meta CAPI, Google Enhanced Conversions), multi-store support and user accounts.

## Architecture

```
Storefront (theme)                 Shopify checkout
  └─ tracker (t.js)                  └─ custom pixel
       │  page views, UTMs               │  checkout events + visitor ID
       │  writes visitor ID to cart      │
       ▼                                 ▼
            POST /api/collect  (Next.js on Vercel)
                         │
                         ▼
                  Supabase Postgres
                         ▲
                         │
Shopify ── orders/* webhooks ──► /api/webhooks/shopify ──► stitching
Backfill script ── Admin GraphQL API ─────────────────────► stitching
                         │
                         ▼
                   /debug page
```

**Identity chain.** The tracker gives each browser a visitor ID (`_ap_vid`). It saves that ID in two places:

- a first-party cookie on the store domain, which the checkout pixel can read
- a cart attribute, which Shopify copies onto the order as a note attribute

Every order can then be traced back to a visitor.

## 2. Collect endpoint: `POST /api/collect`

- Accepts a JSON body containing a single event or a batch of up to 20 events. The tracker sends it with `navigator.sendBeacon` as `text/plain` to avoid CORS preflight, so the endpoint must parse `text/plain` bodies as JSON.
- CORS: allow only the store's domains (from `ALLOWED_ORIGINS`) and respond to `OPTIONS`.
- Validate with `zod`. Reject bodies larger than 32 KB.
- UTMs, click IDs and the external referrer are parsed **on the server** from the event's `url` and `referrer` (`lib/source.ts`), so the tracker stays small.
- Store the batch with the `ingest_events` database function: upsert the visitor (widen first/last seen; set `first_touch` only if it's empty), then insert the events, ignoring duplicate `id`s.
- The Shopify pixel sandbox sends `Origin: null`; accept that only when every event in the batch has `source = pixel`.
- Hash the client IP (`x-forwarded-for`, first value) using `IP_HASH_SALT`.
- Always return `204` quickly. Log validation failures without the payload.
- Ignore obvious bots (user agent matches a bot list).

**Tests:** valid single event, valid batch, duplicate event ID, oversized body, bad origin, invalid payload, `text/plain` body, bot UA.

## 3. Tracking script (`tracker/` → `public/t.js`)

Installed in the theme as `<script src="https://<vercel-domain>/t.js" async></script>`.

- Keep it small (target < 5 KB minified) with no dependencies. Build it with esbuild.
- **Visitor ID:** read the `_ap_vid` cookie or create a UUID. Set it as a first-party cookie on the store's root domain with `SameSite=Lax`, `Secure` and a 395-day expiry, refreshed on each visit.
- **Session ID:** keep in `sessionStorage` plus a last-activity timestamp. Start a new session after 30 minutes idle or when a new UTM or click ID is present.
- **On every page load:** send a `page_view` with URL, path, referrer, UTMs and click IDs parsed from the URL.
- **Cart attribute:** once per session, and whenever the cart changes, call `POST /cart/update.js` with `{"attributes": {"_ap_vid": "<id>"}}` so the ID ends up in the order's `note_attributes`. Skip the call if the cart already has the attribute.
- **Consent:** if `window.Shopify.customerPrivacy` exists, only track when `analyticsProcessingAllowed()` is true. Listen for the `visitorConsentCollected` event.
- Fail silently. The script must never throw in the storefront.

**Tests:** URL/UTM/click-ID parsing, touchpoint detection, session rollover rules and cookie read/write (jsdom).

## 4. Shopify custom pixel (`pixel/`)

Pasted into Shopify admin → Settings → Customer events. It runs in Shopify's sandbox.

- Subscribe to `checkout_started`, `checkout_contact_info_submitted`, `checkout_shipping_info_submitted`, `payment_info_submitted` and `checkout_completed`.
- Read `_ap_vid` with `browser.cookie.get`. If it's missing, create an ID and store it with `browser.cookie.set`.
- Send to `/api/collect` with `checkout_token` and, on `checkout_completed`, the order ID.
- The pixel's privacy setting should be **Analytics** so Shopify enforces consent.

The pixel can't be deployed from code. Keep the source in `pixel/` and add a short README with paste instructions.

## 5. Shopify webhooks: `POST /api/webhooks/shopify`

Topics: `orders/create`, `orders/updated`, `orders/paid`, `orders/cancelled`, `refunds/create`, plus the mandatory privacy topics `customers/data_request`, `customers/redact` and `shop/redact`.

1. Read the **raw** body as text before anything else.
2. Compute base64 HMAC-SHA256 of the raw body with `SHOPIFY_CLIENT_SECRET` and compare it to `X-Shopify-Hmac-Sha256` with `crypto.timingSafeEqual`. Return `401` on mismatch.
3. Check that `X-Shopify-Shop-Domain` equals `SHOPIFY_SHOP_DOMAIN`.
4. Insert into `webhook_events`. If `webhook_id` already exists, return `200` and stop.
5. Upsert the order, run stitching and attribution, and set `processed_at`. On error, record `error` and return `500` so Shopify retries.
6. Respond within 5 seconds.
7. Privacy topics: `customers/redact` deletes or anonymizes that customer's orders (`email_hash`, `customer_id`). `shop/redact` deletes all data. `customers/data_request` is logged for manual handling.

**Tests:** valid HMAC, tampered body, missing header, wrong shop, duplicate webhook ID, each order topic, redact topics. Use recorded fixture payloads, not live calls.

## 6. Stitching and attribution (`lib/stitch.ts`, `lib/attribution.ts`)

Keep these as pure functions that take an order plus candidate data and return a result. The database layer is kept separate.

**Stitching.** Try in order and stop at the first match:

1. `cart_attribute`: `note_attributes._ap_vid` exists and the visitor exists.
2. `checkout_token`: a pixel event has the same `checkout_token`.
3. `customer_history`: an earlier order with the same `customer_id` or `email_hash` is stitched to a visitor. Use that visitor.
4. `none`: leave `visitor_id` null.

**Attribution.** Use the stitched visitor's touchpoints (`is_touchpoint = true`) within a **30-day lookback** before `orders.created_at`.

- `first_touch`: the earliest touchpoint in the window.
- `last_touch`: the latest touchpoint in the window.
- `last_non_direct`: the latest touchpoint whose channel isn't `direct`.
- If there are no touchpoints, write a row with `event_id = null` and `channel = 'direct'`.

**Channel rules** (`lib/channel.ts`, table-driven):

| Signal | Channel |
|---|---|
| `gclid` or `msclkid` | `paid_search` |
| `fbclid` + paid UTM medium, or `ttclid` | `paid_social` |
| `utm_medium` in (`cpc`, `ppc`, `paid`, `paidsearch`) | `paid_search` |
| `utm_medium` in (`paid_social`, `paidsocial`) | `paid_social` |
| `utm_medium` = `email` | `email` |
| referrer is a search engine | `organic_search` |
| referrer is a social site | `organic_social` |
| other external referrer | `referral` |
| none | `direct` |

Re-run attribution whenever an order is updated or a late pixel event arrives for its checkout token.

**Tests:** each stitch path, precedence between paths, lookback boundaries, the channel table and orders with no visitor.

## 7. Backfill script (`scripts/backfill.ts`)

- Run with `npx tsx scripts/backfill.ts --since 2026-01-01 [--dry-run]`.
- Use the Admin GraphQL API (`SHOPIFY_ADMIN_TOKEN`, scope `read_orders`; `read_all_orders` for orders older than 60 days). Page through orders with a cursor and respect the rate-limit `extensions.cost`.
- Upsert orders with `ingested_via = 'backfill'`. Never overwrite rows that came from a webhook with older data.
- Run stitching and attribution. Historical orders usually have no visitor, so most will be `none`. That's expected.
- Resumable: log progress and accept `--after <cursor>`.
- Print a summary with counts by `stitch_method`.

**Tests:** GraphQL-to-row mapping, pagination loop (mocked client), dry-run writes nothing.

## 8. Debug page (`/debug`)

An internal tool, protected with HTTP Basic Auth using `DEBUG_PASSWORD` in `proxy.ts` (Next.js 16 renamed `middleware.ts` to `proxy.ts`).

- Search by order name (`#1001`), order ID, visitor ID or checkout token.
- **Order view:** order summary, `stitch_method`, visitor ID, the three attribution results, and a timeline of the visitor's events (type, time, source, channel, UTMs, URL).
- **Visitor view:** all events and linked orders.
- **Recent view:** the last 50 orders with their stitch method, plus the overall match rate (the share of orders not `none`) for the last 7 and 30 days.
- **Webhook view:** the last 50 `webhook_events`, with errors highlighted.
- Server components only. Queries run with the service role on the server.

**Tests:** auth proxy and data-loading functions.

## Decisions (defaults chosen by owner)

1. **Store domains:** not yet known. Read from `SHOPIFY_SHOP_DOMAIN` and `ALLOWED_ORIGINS`; fill in at the webhook step.
2. **Lookback window:** 30 days, set in one constant.
3. **Consent:** always respect Shopify's Customer Privacy API (tracker) and the pixel's Analytics setting. Safe for EU/UK and harmless elsewhere.
4. **Backfill range:** the last 12 months by default (`--since` overrides). Older than 60 days needs `read_all_orders`.
5. **Storefront:** standard Online Store theme (not headless).
